# 文件组织规则

> 本规则规范本项目的文件组织方式。AI 新增/修改文件时必须遵守，避免规则散乱、重复维护。

---

## 一、文件分工

| 类型 | 放哪 | 特征 | 什么时候读 |
|------|------|------|-----------|
| 全局入口 | AGENTS.md | 最核心的指引：读哪些文件、开发规则、核心原则 | 每次开工自动读 |
| 产品说明 | PRODUCT.md | 产品定位、目标用户、功能范围、做/不做、成功标准 | 每次开工自动读 |
| 设计规范 | DESIGN.md | 布局、配色、字号、组件样式、交互原则 | 画原型/改UI时读 |
| 规则 | 规则/*.md | 具体场景的操作规范（文件组织、项目索引、Git同步、自动化任务、Skill管理、新电脑初始化等） | 操作时读 |
| AI自检 | AI自检清单.md | AI反复犯的问题清单 | 开工前扫、完成后查 |

### AGENTS.md 只放什么

- 项目概述、技术栈、目录结构
- 开发规则（核心原则、路径规则、代码规范、Git提交规则）
- 高风险操作
- 对其他文件的引用指引

### AGENTS.md 不放什么

- 产品功能定义 → 放 PRODUCT.md
- 视觉样式 → 放 DESIGN.md
- 具体场景操作规范 → 放 规则/*.md
- AI犯过的错 → 放 AI自检清单.md

## 二、核心规则：一个内容单元一个独立文件，不叠加

> 这是最重要的文件组织规则，违反这条会导致文件越来越难用。

**什么是"叠加"**：把多个独立的内容单元塞进同一个文件里，用标题分隔。比如把5条灵感写进一个 README.md 里，用 `### 灵感1` `### 灵感2` 分开。

**为什么不叠加**：
- 叠加后文件越来越长，找内容要滚动
- 改一条容易碰到别的条目
- 没法对单条做状态追踪
- 不利于单独引用和复用

**什么情况算"一个内容单元"**：

| 场景 | 一个内容单元 = | 文件粒度 |
|------|--------------|---------|
| 认知/感悟 | 一个独立的认知 | 一个认知一个文件 |
| 灵感/选题 | 一条灵感 | 一个灵感一个文件 |
| 每日总结 | 一天的总结 | 一天一个文件 |
| 决策记录 | 一个决策过程 | 一个决策一个文件 |

**什么情况可以放一个文件**：
- 一份完整的文档（产品说明是一个整体，不分拆）
- 规则文件（Git同步规则是一个整体）
- README/索引文件（只放列表和引用，不放正文内容）

**判断标准**：如果这个内容单元以后会单独被引用、单独改状态、单独拿走用 → 独立文件。如果它永远只是整体的一部分 → 放在一起。

## 三、认知/灵感类文档必须带"原话"

认知、灵感、感悟这类文档，是用户在对话中说出的真实想法，AI 整理成文的。这类文档必须包含"原话"章节，把用户最初说的原话放进去。

- **原话章节**放在文档最前面（前言之后、正文之前）
- 原话是用户当时说的话，保持原样，不改写、不润色、不缩写
- 后面的展开是基于原话的二次整理，但原话是思考的起点，必须保留

**为什么**：原话是那个时刻真实的思考状态，AI 整理后会丢失口语的质感和思考的原始脉络。以后回看时，原话比整理后的文字更能还原"当时是怎么想的"。

## 四、对话自动记录规则

每次与用户对话时，AI 必须主动判断并记录有价值的内容到每日总结。不需要用户触发，AI 自己在对话过程中或对话结束前完成记录。

### 记录什么

| 场景 | 记录到哪 | 记录什么 |
|------|---------|---------|
| 完成了一个完整任务（搭完功能、改完稿子） | `产出/每日总结/YYYY-MM/每日总结-YYYY-MM-DD.md` | 日期 + 做了什么 + 踩的坑 + 沉淀的经验 |
| 对话中有值得提炼的知识点、经验 | 同上 | 同上 |
| 产生了有价值的决策（方案选型、踩坑解决、规则形成） | `决策记录/决策-主题.md` | 决策背景 + 方案对比 + 最终决策 + 决策理由 + 可复用标准 |

### 怎么判断"值得记录"

- ✅ 踩了坑并解决了
- ✅ 做了多方案对比并最终选了一个
- ✅ 形成了可复用的判断标准或方法论
- ✅ 完成了一个完整功能
- ❌ 纯闲聊、重复确认、格式调整等无实质内容

### 记录格式

**每日总结**（每天一个文件，追加式维护）：
```
# 每日总结 - YYYY-MM-DD

### 今日要点

**1. [事项小标题]**

[做了什么，一段话说清。要写具体：用了什么技术/工具、改了什么文件、关键参数是什么，不要只写"搭了XX功能"]

> [踩的坑 / 沉淀的经验 / 可复用的方法论，用 blockquote 框出。要写具体：根因是什么、怎么解决的、可复用的判断标准是什么]

### 下一步

- [ ] [待办事项，从对话中提取用户提到"接下来要做的"内容]
```

**决策记录**（一个决策一个文件，偶发）：
```
# [决策标题]

> 日期：YYYY-MM-DD

## 问题背景
[为什么需要做这个决策]

## 方案对比
[列2-3个方案，对比利弊]

## 最终决策
[选了什么，为什么]

## 可复用的判断标准
[这个决策沉淀了什么可复用的方法论]
```

### 记录时机

- 在完成一个完整任务后
- 在对话即将结束时（用户说"好了""先这样""下次聊"等收尾语）
- 不需要在每句话后都记，按"一个完整任务"为单位记

### 注意

- 同一天多次对话追加到同一个日期下，不重复建日期标题
- 记录要简洁，不写流水账，只记有价值的要点
- 每日总结按月份子目录归档，写到 `产出/每日总结/YYYY-MM/每日总结-YYYY-MM-DD.md`；决策记录写到 `产出/决策记录/`，按需创建
- AI 生成每日总结时，同步往 `产出/每日总结/README.md` 索引表格顶部追加一行（日期+摘要+链接）

## 五、索引维护规则

> 多文件目录必须有索引（README.md），让人和AI不用逐个翻文件就能知道"有哪些、什么状态、在哪"。

### 哪些目录需要索引

需要长期跟踪追溯、文件会持续增长的目录，都要建索引。

**判断标准**：
- 文件数 ≥ 3 且会继续增长 → 必须建索引
- 文件数少且固定不增长 → 不需要
- 收件箱性质（消化完即流转） → 不需要

### 两种维护方式

**1. 自动同步**（状态存在后端的目录）
- 状态变更时后端自动重写索引
- 无需人工维护，无需 AI 追加

**2. 追加式**（其他所有目录）
- AI 在新增文件时，顺手在对应索引追加一行
- 不需要定时任务
- 新增文档 → 在对应子目录索引追加一行 + 在总索引（如有）追加一行

### 索引文件的内容规范

- 索引只放"标题 + 链接（+ 状态/摘要）"，不放正文
- 状态字段必须来自权威数据源（后端API/标记文件），不从文件存在性推断业务状态
- 文件存在性（✓/—）可以单独列，与状态独立
- 索引顶部写明维护方式和数据来源

## 六、新增/修改文件时的检查动作

### 1. 新建文件前先想：这是什么类型？

- 是规则标准？→ 放 `规则/` 目录
- 是产品文档？→ 放 PRODUCT.md 或单独的产品文档
- 是全局入口指引？→ 放 AGENTS.md（但要克制，能拆出去就拆出去）
- 是AI犯过的错？→ 放 AI自检清单.md
- 是认知/灵感/感悟？→ 独立文件，带原话，放对应目录

### 2. 发现重复内容怎么办

- 两处写了同样的规则 → 合并到一处，另一处改成引用
- 不知道合并到哪一处 → 优先放对应分类文件，其他地方改成引用
- 合并后删除被废弃的文件，不要留着"备份"

### 3. AGENTS.md 超过 250 行怎么办

检查有没有该拆出去的内容：
- 大段的设计规范 → 拆到 DESIGN.md
- 大段的产品功能 → 拆到 PRODUCT.md
- 大段的具体场景操作规范 → 拆到 规则/ 目录
- 拆完后 AGENTS.md 里只留一句引用

### 4. 新增规则文件怎么命名

- 用中文，直白描述内容（如 `Git同步规则.md`、`文件组织规则.md`）
- 不用英文缩写，不用 SETUP、README 这类通用名
- 名字能一眼看出是做什么的

## 七、多项目规则同步机制

> 多个项目各自演进，改了一边的规则要不要同步到另一边？这里定机制。

### 核心原则：地基包是通用规则的唯一源

- **通用规则**（跨项目通用的，如"确认规则""一个内容单元一个独立文件"）→ 改地基包，各项目拉取合并
- **项目特有规则**（如工作台的抖音写稿规则、raisenote的商业模式规则）→ 各项目自己维护，不进地基包，不同步

### 怎么标注规则的来源

在规则文件里，来自地基包的章节用注释标注：

```markdown
<!-- source: project-base -->
## 五、核心规则：一个内容单元一个独立文件
...
<!-- /source: project-base -->
```

项目自己加的规则不标注。这样AI对比时知道哪些该同步、哪些不该动。

### 同步流程

**方向1：项目 → 地基包（项目里改了通用规则）**

1. 在项目里改了规则
2. 判断"这条是不是跨项目通用的"
3. 是 → 告诉AI"同步到地基包" → AI改地基包对应章节 → 提交地基包
4. 否 → 不动地基包

**方向2：地基包 → 项目（地基包更新了，项目要不要拉）**

1. 项目开工时，AI读规则文件，发现标注了 `source: project-base` 的章节
2. AI对比地基包最新版和项目里的版本
3. 有差异 → 提醒用户"地基包的XX规则更新了，要不要同步"
4. 用户同意 → AI合并更新 → 用户确认

### 什么时候触发同步检查

- **项目开工时**：AI读规则文件，发现 `source: project-base` 标注 → 主动对比地基包
- **用户说"同步规则"时**：AI全面对比
- **不需要定时任务**：开工时检查就够了，不需要后台跑

### 判断"该不该进地基包"的标准

| 进地基包 | 不进地基包 |
|---------|-----------|
| 跨项目通用的（不管什么项目都要遵守） | 项目特有的（具体业务规则） |
| AI协作元规则（让AI"变聪明"的规则） | 产品定义（每个项目不同） |
| 工程规范（路径、命名、提交、自检） | 技术选型（每个项目不同） |

跟当初建地基包时的判断标准一致。

# Skill 管理规则

> 本规则规范本项目下 opencode skill 的创建、存放和管理。AI 创建或修改 skill 时必须遵守。
> 不使用 opencode 的项目跳过本文件。

---

## 一、存放位置：分层存放（项目专属 vs 通用）

skill 按**项目专属 vs 跨项目通用**分层存放：

| 类型 | 存放位置 | opencode 加载范围 | 跟谁同步 |
|------|---------|------------------|---------|
| 项目专属 skill | `<项目>/.opencode/skills/<skill名>/SKILL.md` | 仅在该项目目录下生效 | 跟该项目的 git |
| 通用 skill | `~/.config/opencode/skills/<skill名>/SKILL.md` | 所有项目都加载 | 见第五节同步方案 |

**判断作用域**：
- 只在某个项目用 → 放该项目的 `.opencode/skills/`
- 多个项目都会用 → 放全局 `~/.config/opencode/skills/`

**为什么分层而不是全放全局**：
- 项目专属 skill 只在对应项目加载，避免在别的项目里注入无关的 description（浪费 token、可能误触发）
- 各项目的专属 skill 跟着各项目 git 走，互不干扰
- 通用 skill 集中放一处，跨项目复用

---

## 二、创建 skill 前的防重复检查

创建新 skill 前，先判断作用域，再扫对应目录有没有同名 skill：

- 项目专属 → 扫 `<项目>/.opencode/skills/`
- 通用 → 扫 `~/.config/opencode/skills/`

有同名 → 不要重建，改现有的。同时检查有没有**触发关键词撞车**的 skill（见第三节"撞车消歧"）。

## 三、SKILL.md 写作规范

### 文件结构

```
<对应目录>/<skill名>/
└── SKILL.md
```

skill 目录名用英文（如 `weekly-report`），SKILL.md 是唯一文件。

### frontmatter（必须）

```yaml
---
name: skill名（英文，跟目录名一致）
description: 中文描述，必须包含触发关键词
---
```

**description 的写法**：
- 用中文（用户会用中文触发）
- 必须包含用户会说的触发关键词（如"写周报""出周报""生成本周周报"）
- 说明触发场景（"用户说XX时触发"）
- **项目专属 skill 必须加作用域限定**（如"仅在 XX 项目目录下使用""在其他项目目录下不要触发"），防止在其他项目里误触发
- 通用 skill 不加作用域限定（所有项目都该加载）

### 撞车消歧（重要）

不同 skill 的触发关键词可能撞车（尤其项目专属 skill 在自己项目里，跟通用 skill 同时加载时）。撞车时必须在 description 里手动消歧——明确说"用户说XX时走另一个 skill，不要触发本 skill"。

**例子**：
- `zentao-story-import`（禅道录需求）和 `backlog-import`（需求池）都会被"录入需求"触发
- `zentao-story-import` 的 description 里加："注意：用户说'录入需求池''需求池加一条'（明确带'需求池'字样）时走需求池 skill（backlog-import），不要触发本 skill"

**判断要不要消歧**：创建新 skill 时，扫一遍当前会加载的 skill 的 description，看有没有触发关键词重叠的。有重叠就加消歧说明。

### 正文结构

默认推荐以下 7 段式结构（适合大多数 Skill）：

```
# [skill 中文名]

## 适用场景
什么时候用这个 skill。

## 触发条件
用户说什么话时触发。

## 前置条件
执行前需要什么（读哪些文件、装什么依赖、拿到什么输入）。

## 输入格式
用户要提供什么（参数、文件、口述内容）。

## 执行流程
具体步骤，每步可执行，不写空话。
"第一步读取X文件，第二步调Y接口，第三步逐行创建" ✅
"分析数据并给出建议" ❌

## 输出格式
产出长什么样（文件路径、文件结构、内容模板）。

## 注意事项
容易踩的坑、边界情况、特殊处理。
```

**复杂 Skill 可选其他结构模式**：当 7 段式不够用时，从下表选一个更贴合的组织骨架，7 段式的段落可以作为骨架内的子章节灵活嵌入：

| 模式 | 适用场景 | 结构骨架 |
|------|---------|---------|
| **流程型**（默认） | 有明显先后顺序的步骤 | 适用场景 → 触发条件 → 执行流程 Step1→Step2... |
| **任务型** | 同一类下的多个独立并列操作 | Overview → Quick Start → 任务A → 任务B... |
| **规范型** | 标准/规范/规格说明 | Overview → Guidelines → Specifications → Usage（通常拆成独立规则文件，SKILL.md 只引用） |
| **能力型** | 多个相关功能集成 | Overview → Core Capabilities → 1.功能A → 2.功能B... |

**怎么选**：
- 默认用流程型（7 段式）
- 同一类下有多个并列操作、无明显先后 → 任务型
- 是标准/规范说明 → 规范型（通常拆成独立规则文件）
- 是多个相关功能打包 → 能力型

### 语言

- 全部用中文编写：description、正文、注释
- skill 目录名用英文（兼容性好，路径不易出错）
- 已有的英文 skill 不强制改中文，能正常工作即可；新建或大改时统一用中文

## 四、修改和删除 skill

### 修改

- 先看 skill 在哪个目录（项目专属 vs 通用）
- 项目专属 → 改 `<项目>/.opencode/skills/<skill名>/SKILL.md`，在对应项目提交 git
- 通用 → 改 `~/.config/opencode/skills/<skill名>/SKILL.md`，按第五节方案同步
- 改完后不需要重启 opencode，下次触发自动加载新版

### 删除

- 确认这个 skill 真的没用了再删
- 项目专属 → 删 `<项目>/.opencode/skills/<skill名>/` 目录，在对应项目提交
- 通用 → 删 `~/.config/opencode/skills/<skill名>/` 目录，按第五节方案同步
- 删完后扫一遍 AGENTS.md、操作手册等文档，看有没有引用这个 skill 的地方，一并清理

## 五、通用 skill 的跨电脑同步

通用 skill 在全局目录 `~/.config/opencode/skills/`，换电脑时要同步。有两种方案：

### 方案A：独立 git 仓库

把全局 skill 目录放进一个独立 git 仓库，换电脑 clone。

- 优点：通用 skill 跟项目解耦，独立演进
- 缺点：多一个仓库要维护，容易忘了提交
- 适合：通用 skill 多、跟任何项目都不强绑定的场景

### 方案B：软链绑定某个项目

让全局目录软链指向某个项目的镜像目录，通用 skill 跟着该项目的 git 走，换电脑 git pull 即同步。

**怎么做：**
```bash
# 删掉全局目录（先备份）
rm -rf ~/.config/opencode/skills
# 创建软链，指向某项目的镜像目录
ln -s /path/to/项目/.skills-mirror/skills ~/.config/opencode/skills
```

**机制：**
- 全局目录 = 某项目的镜像目录（同一份文件，两个路径）
- 写全局 skill = 写该项目的镜像目录 → 跟着该项目 git 提交 → 换电脑 git pull 即同步

**适用条件：**
- 有一个项目愿意承载全局 skill（通常是你的核心工作项目）
- 通用 skill 跟该项目关联度较高（即使该项目不用，放这里也无害）

**限制：**
- 全局目录只能指向一个地方，所以**只有一个项目能用软链机制承载通用 skill**
- 其他项目想创建通用 skill，直接写到承载项目的镜像目录（通过全局软链访问）

**为什么推荐软链：**
- 不用多维护一个仓库（借用项目的 git）
- 通用 skill 跟该项目一起换电脑同步，不会漏

> 软链是"借用一个项目的 git 来管理通用 skill"的思路。本质是把"通用 skill 的同步问题"转化为"某项目的 git 同步问题"，借力已有机制，不新建机制。

## 六、常见问题

### Q：skill 和 agent 有什么区别？

- **skill** 是"流程脚本"——用户说一句话触发，按固定流程执行，产出固定结果。像"周报生成""版本更新记录"。
- **agent** 是"协作者"——在特定阶段介入，有判断能力，能跟主 agent 协作。像"需求拆解员""测试员"。

简单判断：流程固定、不需要交互 → skill；需要判断、跟主 agent 配合 → agent。

### Q：一个流程不确定做成 skill 还是 agent，怎么办？

先不做。等这个流程跑了 2-3 次、套路稳定了，再固化。固化时按上面的标准判断。

### Q：为什么不再把所有 skill 都放全局？

以前是全放全局，靠 description 关键词区分触发。问题是：在 A 项目对话时也会加载 B 项目专属的 skill description，浪费 token，还可能误触发。改成分层后，项目专属的只在该项目加载，干净很多。

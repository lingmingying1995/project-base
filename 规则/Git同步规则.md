# Git 同步规则（AI 必读）

> 这个文档解决一个核心问题：**什么时候 commit + push，怎么 commit + push**。

---

## 一、核心原则：攒着改，触发时统一提交

**平时只管改文件，不要改一次提交一次。** 等以下任一触发条件出现，再按标准流程统一 commit + push：

### 触发提交的条件

1. **用户说"push"**（或"提交""同步一下"等明确指令）
2. **定时同步任务触发**（如配了定时同步脚本）
3. **对话即将结束**（用户说"好了""先这样""下次聊"等收尾语）
4. **准备切换电脑**（要关机、要离开当前电脑）

### 用户说"提交"是什么意思

**= commit + push 一气呵成，不要提交完停下来问"要推送吗"。** 用户说"提交"就是要把改动同步到远端，不是只想本地 commit。触发后直接走标准提交流程（add → commit → push），一次做完。

例外（这些情况可以问一次）：
- 第一次推送到新远程仓库
- 需要 force push
- 当前分支没有上游
- push 被拒（远端有新提交，需要先 pull）—— 这种告诉用户原因，问"要不要 pull 后重试"

### 平时怎么做

- 改文件就改，不用管 git
- 新建文件就建，不用管 git
- AI 完成任务后不用主动 commit，继续等下一个任务
- **但心里要有数**：知道当前有哪些改动还没提交（`git status` 随时可查）

### 为什么不每次都提交

- 一天改十几次，提交十几次，git 历史会很碎
- 很多改动是中间状态，单独提交没意义
- 个人项目，攒一批一起提交更清晰

---

## 二、标准提交流程（触发时执行）

当出现上述触发条件时，按以下流程操作：

```bash
# 1. 查看当前有哪些改动
git status

# 2. 添加所有改动（个人项目，简单粗暴）
git add -A

# 3. 提交（message 用中文，按下方格式写）
git commit -m "类型: 说明"

# 4. 推送到远端
git push
```

### 如果一次提交包含多个改动

在 commit message 里列清楚改了什么，用 `+` 连接：

```bash
git commit -m "feat: 新增XX功能 + 修复YY问题 + 更新文档"
```

### 如果 push 失败（远端有新提交）

```bash
# 先拉取合并
git pull
# 如果有冲突，解决冲突后：
git add -A
git commit -m "merge: 合并远端更新"
git push
```

---

## 三、开始工作前必做

每次开始工作前（打开 opencode 准备干活时），**先拉取最新代码**：

```bash
git pull
```

避免本地是旧代码，改完 push 时冲突。

---

## 四、commit message 格式

| 类型 | 说明 | 示例 |
|------|------|------|
| `feat` | 新增功能 | `feat: 新增XX功能` |
| `fix` | 修复问题 | `fix: 修复XX报错` |
| `docs` | 文档更新 | `docs: 更新PRODUCT.md` |
| `refactor` | 重构代码 | `refactor: XX模块重构` |
| `style` | 样式调整 | `style: 调整按钮间距` |
| `sync` | 定时同步 | `sync: 2026-08-01` |

一次提交多个改动时，选最主要的类型，说明里用 `+` 列出各项。

## 五、多电脑协作（如适用）

如果项目在多台电脑上开发（如工作电脑+家用电脑）：

### 切换电脑时的注意事项

1. **离开前**：确保已 push（手动或定时任务）
2. **开工前**：先 `git pull`

### 最容易踩的坑

**写完文件直接关机，没 commit。** 文件还在工作区，但没进 git 历史，push 不会上传，另一台电脑拉不到。

**对策**：结束工作前，**必须**跑一遍标准提交流程。哪怕只改了一个字，也要 commit + push。

---

## 六、AI 自检清单（用户说 push 或对话收尾时必查）

当用户说"push"或对话即将结束时，AI 执行提交前必须自问：

- [ ] **这次攒了哪些改动？** → 跑 `git status` 看清楚
- [ ] **新建了哪些文件？** → 确认都在 "Changes to be committed" 里
- [ ] **修改了哪些文件？** → 确认都在 "Changes to be committed" 里
- [ ] **commit message 写清楚了吗？** → 列出主要改动，不要只写"更新"
- [ ] **push 成功了吗？** → 看到 `main -> main` 才算成功
